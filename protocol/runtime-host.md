# Runtime host protocol

Host protocol version 4 connects a browser to the local Bun host at `/api/runtime` over a same-origin WebSocket. Each connection owns one Bun worker thread and one episode or standalone world. The Rust N-API module owns Rapier, body/joint lifetimes, actuation and contact feedback. TypeScript owns action selection, episode scheduling and independent task scoring. Browser rendering receives measured state and does not advance another physics world.

Requests are JSON `{ id, method, payload }`; replies are `{ id, value }` or `{ id, error: { message, code?, detail? } }`. Client IDs are positive integers. Host callbacks use negative IDs and receive the same reply envelope. Policy failures preserve their policy code/detail across the transport. The version is required when opening a session. Image uploads use the recording packet transport. Frame-bearing host replies and callbacks use the binary envelope below.

## Episode commands

- `open`: `{ version: 4, config, plan, source, name, sink, recording? }`. Source is `teacher`, `manual` or `client`. The sink is an array of the requested `observation`, `action` and `diagnostic` callbacks. Headless runs use an empty array, and visual-only runs request observations. The immutable resolved plan contains configuration, resolved scene, task and appearance. The host validates configuration and checks the plan against local resolution before creating the shared Episode. The reply contains world metadata and an initial episode frame. An optional recording ID binds the episode to a host-registered writer. IDs are capabilities allocated by the run coordinator.
- `step`: run exactly one shared `Episode.step()`. Manual input contains the current key list and a hold sequence number. Concurrent steps/runs are rejected. The reply is the measured episode frame after the step and its due callbacks complete.
- `advance`: `{ ticks }`, a positive safe integer, for host teachers only. Run up to that many consecutive shared `Episode.step()` calls within an 8-ms host work budget, returning the measured frame and its actual tick. Planning can yield beyond the budget within one step. Pause or episode completion ends the batch; pending planning still honors the shared pause gate. The UI reserves due ticks before the request and returns unprocessed ticks to its accumulator only while the same playback clock is running. Every control, observation and scoring tick still executes; only transport frames are coalesced. Concurrent steps/runs are rejected.
- `run`: drain the shared Episode loop and return its final episode frame after source completion and host recording have drained. Browser collection and headless CLI execution use this command. Sensor and policy callbacks, pause and stop remain live while the request is pending.
- `pause`, `resume`: control the shared episode gate. They remain available while inference, capture or planning is awaited. Pause replies with the measured frame at the acknowledged boundary; `Episode.settled()` awaits this acknowledgement without waiting for pending inference. Simulation time does not advance after that boundary until resume.
- `finish`: `{ outcome: "stopped", reason }`. Only interruption may be requested by the client; task success is scored by the host. Pending source work is cancelled and completion drains before replying.
- `settled`: await the source's completion callback.
- `appearance`: apply a theme only before execution, preserving the existing appearance permissions.
- `dispose`: finish/drain the episode and free its native world.

Host callbacks are `source.initialize`, `source.observe`, `source.next`, `source.cancel`, `source.end` and, when requested, `sink.observation`, `sink.action`, `sink.diagnostic`. A registered host recording sends only observation callbacks to the browser. Its action and diagnostic rows are delivered directly from the Bun worker to the registered host writer in batches of at most 128 rows. The writer serializes these batches with image/video uploads and acknowledges backpressure. Final, stopped and disposed episodes drain the remaining rows. Their payload is `{ frame, data }`. The browser installs the measured frame before capturing sensor pixels or invoking a policy callback. The host awaits the result before continuing the episode. Source factories and sinks keep their existing contracts; callback data never substitutes targets for measured state.

An episode frame contains `physics`, `phase`, `stage`, `result`, observation/action counts, independent scoring and optional teacher diagnostics. The browser physics frame contains its integer tick, measured State16D, last Action16D target, body poses, velocities/COM and both TCPs. Complete collider transforms, actuator/finger diagnostics and contact manifolds/feedback stay in the host for control, scoring and recording. The host Simulation produces a complete WorldSnapshot, and the browser WorldView exposes WorldMeasurements. The final world snapshot stores both end-effector poses in `tcps` in arm order. Static metadata contains body/collider identifiers, primitive shapes, mass properties and robot membership. These are privileged world data for rendering and diagnostics. Standard policy observations retain only the declared images, measured State16D and camera transform defined by the policy schema.

## Binary frame envelope

Frame-bearing host messages are binary WebSocket frames. The first four bytes contain the little-endian uint32 JSON header length. UTF-8 JSON follows and is padded to an eight-byte boundary. The remainder contains little-endian float64 measurements. The header contains `message`, retaining the RPC envelope with the numeric frame replaced by null, and `location`, identifying `world`, `episode`, `opened` or `callback`.

The numeric frame starts with `[tick, bodyCount, 0, 0]`, State16D and Action16D. Each body contributes `[id, position(3), quaternion(4), linearVelocity(3), angularVelocity(3), worldCOM(3)]`. The final sixteen values contain the two TCPs, each ordered `[x,y,z,gap,qx,qy,qz,qw]`. Body and collider identities, primitive geometry and physical mass metadata are sent once on open.

## Standalone world commands

`world.open` accepts `{ version: 4, config }`, where config is the resolved DOM-free WorldConfig. `world.step`, `world.apply`, `world.body` and `world.dispose` support independent sensor/physics tools and fixtures. Apply contains an absolute Action16D and its continuous flag. Body commands address an object index and explicit pose/velocity changes; the teacher and task scoring never use these commands to carry objects or claim success. Each successful state-changing command returns the measured physics frame.

## Native module boundary

The constructor consumes resolved physical configuration and neutral primitive/frame descriptions generated from the shared robot geometry. Rust creates all Rapier bodies, colliders and joints. Stepping updates waist/arm motors, gravity feedforward and compliant jaw coupling before the fixed Rapier timestep. The synchronous N-API call writes float64 values into a reusable caller-owned buffer. It returns the required element count. If the buffer is too small, the caller grows it and reads the frame again without taking another physical step. Measurements are decoded into independent objects, preserving retained action and diagnostic rows. No DOM, renderer, teacher or task is required by the Rust core.

Infrequent setup/mutation commands use JSON. Planner shape queries use one synchronous 23-value Float64Array: two four-value shape descriptions, two seven-value poses, then prediction distance. Shape codes are cuboid 0 (`sizeX,sizeY,sizeZ`), cylinder 1 (`height,radius,0`) and sphere 2 (`radius,0,0`); poses are `x,y,z,qx,qy,qz,qw`. A finite return value is contact distance; NaN denotes no contact within prediction. The scratch array is private to its Bun thread and reused only across synchronous calls. This avoids JSON serialization in the collision-planning loop without changing collision thresholds.

## Identity and lifecycle

The environment is `stackling-v5.4`. Its measured State16D and absolute Action16D are defined in the [whole-body contract](whole-body.md). Recording schema 10 stores the build identity in `provenance.physics`, including source hash, binary SHA-256, Rust compiler identity, flags, platform and architecture. The compatibility fingerprint includes Rust sources/Cargo lockfile, the native bridge and build identity. Original Profiles and recordings retain their original identities.

`bun run build:physics` builds the locked release crate and writes ignored native artifacts under `.tmp/physics/`. The loader rejects stale sources or a binary checksum mismatch. Restart the Bun host after rebuilding Rust; a running worker retains its loaded module and existing worlds. Closing a connection rejects pending callbacks and frees its native world; executor shutdown terminates its worker threads. Build artifacts and generated results are not committed.

The complete native frame layout is `[tick, bodyCount, colliderCount, objectCount]`, State16D, Action16D, body records, collider records `[id,x,y,z,qx,qy,qz,qw]`, the two TCP records, fourteen nine-value actuator diagnostics, two pairs of six-value finger diagnostics, and two object-by-finger arrays of five-value contact feedback. Diagnostic field order follows the dataset definitions in the [whole-body contract](whole-body.md). A final pair count precedes variable solver contacts. Each pair stores collider IDs and a manifold count. A manifold stores its normal, friction and point count. Each point stores current signed separation, solved impulse and two local three-value contact positions. Separation and manifold normal are reprojected from the current collider/subshape poses; stale cached distances are excluded. Pairs with no active solver contacts are omitted.
